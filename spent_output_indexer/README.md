# Open Bitcoin Metrics: Spent Output Indexer

This directory contains the internal indexing script:

```text
obm_spent_output_indexer.py
```

The script builds a persistent SQLite database that supports the generation of several Open Bitcoin Metrics (OBM) time series related to spent outputs, coin age, fees, issuance, and miner revenue.

This script is **not itself a published OBM metric**. It is an internal state builder used by small export scripts that generate individual metric CSV files.

## Purpose

Several Bitcoin metrics require resolving each transaction input to the previous output it spends. This is computationally expensive because it requires scanning the blockchain in order and maintaining a live outpoint state.

Examples include:

```text
obm_cdd_btcxdays_daily
obm_spent_value_btc_daily
obm_dormancy_days_daily
obm_bincdd365d_btc_daily
obm_fees_btc_daily
obm_issuance_btc_daily
obm_miner_revenue_btc_daily
```

Instead of repeating the same expensive blockchain scan for each metric, `obm_spent_output_indexer.py` performs a single persistent scan and stores daily aggregate values in SQLite. Later, lightweight export scripts read the SQLite database and write standard OBM CSV files.

## What the indexer stores

The indexer maintains four main groups of tables:

1. a live outpoint table;
2. daily aggregate tables;
3. age-band aggregate tables;
4. processing metadata.

### Live outpoint state

The main live-state table is:

```text
outpoints
```

It stores the currently unspent outputs needed to resolve future transaction inputs.

Each row contains:

| Column | Description |
|---|---|
| `txid` | Transaction identifier of the output |
| `vout` | Output index within the transaction |
| `value_sats` | Output value in satoshis |
| `created_time` | Block timestamp of the block that created the output |
| `created_height` | Block height of the block that created the output |

The primary key is:

```text
(txid, vout)
```

When a transaction input spends a previous output, the indexer retrieves the previous output value and creation timestamp, uses them to update daily aggregates, and deletes the spent output from the live table.

### Daily aggregate table

The main aggregate table is:

```text
daily_aggregates
```

It contains one row per UTC date with activity observed by the indexer. Dates with no indexed activity may be absent. Export scripts decide whether absent dates should be exported as zero or as missing, depending on the metric.

The table includes the following fields:

| Column | Description |
|---|---|
| `date` | UTC calendar date |
| `spent_value_sats` | Total value of spent outputs, in satoshis |
| `spent_output_count` | Number of spent outputs |
| `cdd_sats_days` | Coin Days Destroyed, stored as satoshi-days |
| `spent_output_age_days_sum` | Sum of spent-output ages in days |
| `spent_value_365d_sats` | Value of spent outputs aged at least 365 days |
| `cdd_365d_sats_days` | CDD generated by outputs aged at least 365 days |
| `spent_value_155d_sats` | Value of spent outputs aged at least 155 days |
| `cdd_155d_sats_days` | CDD generated by outputs aged at least 155 days |
| `spent_value_lt_155d_sats` | Value of spent outputs younger than 155 days |
| `cdd_lt_155d_sats_days` | CDD generated by outputs younger than 155 days |
| `fees_sats` | Total transaction fees in satoshis |
| `coinbase_output_sats` | Total coinbase output value in satoshis |
| `issuance_sats` | Realized issuance in satoshis |
| `negative_age_outputs` | Count of spent outputs whose apparent age was floored to zero |

### Age-band aggregate table

The table:

```text
daily_age_band_aggregates
```

stores daily spent-output activity by age band.

Each row is indexed by:

```text
(date, age_band)
```

and stores:

| Column | Description |
|---|---|
| `date` | UTC calendar date |
| `age_band` | Age-band label |
| `spent_value_sats` | Total spent value in that age band |
| `cdd_sats_days` | CDD generated by that age band |
| `spent_output_count` | Number of spent outputs in that age band |

The current age bands are:

```text
0d_1d
1d_1w
1w_1m
1m_3m
3m_6m
6m_1y
1y_2y
2y_3y
3y_5y
5y_7y
7y_10y
10y_plus
```

### Metadata and processed blocks

The table:

```text
metadata
```

stores indexer metadata, including:

| Key | Meaning |
|---|---|
| `state_schema_version` | SQLite schema version |
| `indexer_id` | Expected value: `obm_spent_output_indexer` |
| `definition_version` | Internal definition version |
| `release_version` | OBM release version used by exporters |
| `last_processed_height` | Last block height committed to the database |
| `last_processed_hash` | Hash of the last processed block |
| `last_processed_time` | Timestamp of the last processed block |
| `last_processed_date` | UTC date of the last processed block |
| `max_processed_date` | Maximum UTC date observed in processed blocks |
| `last_run_utc` | Last execution time in UTC |

The table:

```text
processed_blocks
```

stores block-level processing metadata:

| Column | Description |
|---|---|
| `height` | Block height |
| `hash` | Block hash |
| `block_time` | Block timestamp |
| `block_date` | UTC date derived from block timestamp |

## Metrics supported by the indexer

The indexer stores enough information to export several OBM series.

### Directly exportable from `daily_aggregates`

| OBM series | Source column |
|---|---|
| `obm_cdd_btcxdays_daily` | `cdd_sats_days / 100000000` |
| `obm_spent_value_btc_daily` | `spent_value_sats / 100000000` |
| `obm_fees_btc_daily` | `fees_sats / 100000000` |
| `obm_issuance_btc_daily` | `issuance_sats / 100000000` |
| `obm_miner_revenue_btc_daily` | `coinbase_output_sats / 100000000` |
| `obm_bincdd365d_btc_daily` | `spent_value_365d_sats / 100000000` |
| `obm_spent_output_count_daily` | `spent_output_count` |

### Derived from exported series or aggregate columns

| OBM series | Formula |
|---|---|
| `obm_dormancy_days_daily` | `cdd_btcxdays / spent_value_btc` |
| `obm_fee_share_miner_revenue_ratio_daily` | `fees_btc / (issuance_btc + fees_btc)` |
| `obm_cdd_per_supply_days_daily` | `cdd_btcxdays / supply_btc` |
| `obm_lth_spent_value_share_155d_daily` | `spent_value_155d / spent_value_total` |
| `obm_lth_cdd_share_155d_daily` | `cdd_155d / cdd_total` |

### Exportable from `daily_age_band_aggregates`

The age-band table can support future series such as:

```text
obm_spent_value_age_band_btc_daily
obm_cdd_age_band_btcxdays_daily
obm_spent_output_count_age_band_daily
```

## Definition of key internal quantities

### Spent output value

For each non-coinbase transaction input, the indexer identifies the previous output it spends. The spent value contribution is the value of that previous output:

```text
spent_value_i = previous_output_value_i
```

Daily spent value is the sum of these values over all spent outputs assigned to a UTC date.

### Coin Days Destroyed

For each spent output `i`, the indexer computes its age in days as:

```text
age_i = max(0, (spent_time_i - created_time_i) / 86400)
```

Then:

```text
CDD_i = value_i * age_i
```

The indexer stores this internally as satoshi-days:

```text
cdd_sats_days_i = value_sats_i * age_i
```

Export scripts convert satoshi-days to BTC-days by dividing by 100,000,000.

### Transaction fees

For each non-coinbase transaction:

```text
fee = sum(input values) - sum(output values)
```

Since the indexer already resolves previous outputs, the input values are available during transaction processing.

### Miner revenue

Miner revenue in BTC is the total coinbase output value:

```text
miner_revenue = coinbase_output_value
```

The indexer stores this as:

```text
coinbase_output_sats
```

### Issuance

Realized issuance is computed as:

```text
issuance = coinbase_output_value - fees
```

The indexer stores this as:

```text
issuance_sats
```

This distinguishes newly issued BTC from fees, which are transfers of already existing BTC.

## Historical duplicate transaction IDs

Early Bitcoin contains historical duplicate coinbase transaction IDs. These can produce duplicate `(txid, vout)` pairs.

The indexer handles this by overwriting the earlier live outpoint entry with the later one and recording the event in metadata. The overwritten output is not counted as spent and does not generate spent value or CDD.

This behavior is necessary for reproducing effective historical outpoint lookup semantics and avoiding failure on known pre-BIP30 duplicate coinbase edge cases.

## Timestamp convention

The indexer assigns blocks to dates using the UTC date derived from the block timestamp returned by Bitcoin Core:

```text
date = UTCDate(block_time)
```

All daily aggregates use this timestamp convention.

Because Bitcoin block timestamps are not strictly monotonic in block height, the script uses a height margin when selecting the target processing height for a requested end date.

## Command-line usage

### First historical build

```bash
python3 obm_spent_output_indexer.py \\
  --end_date 2024-01-31 \\
  --state_db cache/obm_spent_output_indexer.sqlite \\
  --reset_state_db \\
  --commit_every 10000 \\
  --progress_every 1000
```

### Incremental update

```bash
python3 obm_spent_output_indexer.py \\
  --end_date 2024-02-01 \\
  --state_db cache/obm_spent_output_indexer.sqlite \\
  --commit_every 1000 \\
  --progress_every 1000
```

### Daily automated update

```bash
python3 obm_spent_output_indexer.py \\
  --end_date "$(date -u -d yesterday +\\%F)" \\
  --state_db cache/obm_spent_output_indexer.sqlite \\
  --min_confirmations 100
```

## Command-line arguments

| Argument | Description |
|---|---|
| `--end_date` | Target UTC end date, inclusive |
| `--state_db` | Path to the persistent SQLite database |
| `--reset_state_db` | Delete and rebuild the database from genesis |
| `--release_version` | OBM release version stored in metadata |
| `--rpc_host` | Bitcoin Core RPC host |
| `--rpc_port` | Bitcoin Core RPC port |
| `--rpc_user` | Bitcoin Core RPC username |
| `--rpc_password` | Bitcoin Core RPC password |
| `--datadir` | Bitcoin Core data directory, used to locate `.cookie` |
| `--cookie_path` | Explicit path to Bitcoin Core `.cookie` file |
| `--height_margin` | Extra blocks processed after the approximate end-date height |
| `--min_confirmations` | Number of confirmations required before processing tip-adjacent blocks |
| `--progress_every` | Print progress every N processed blocks |
| `--commit_every` | Commit SQLite changes every N processed blocks |

The optional `--start_date` argument may be accepted by some versions for logging or sanity checks, but the indexer always processes from genesis on a fresh database or resumes from the last processed block in the state database.

## Persistence and interruption

The indexer is designed to be interrupted and resumed.

Progress is periodically committed to SQLite according to:

```text
--commit_every
```

For example:

```text
--commit_every 1000
```

means that every 1,000 processed blocks are committed. If the script is interrupted, the next run resumes from the last committed block.

To resume, rerun the command without:

```text
--reset_state_db
```

Using `--reset_state_db` deletes the previous database and starts again from genesis.

## Chain consistency check

On each run, the indexer checks that the last processed block hash stored in the SQLite database still matches the block hash currently reported by Bitcoin Core at the same height.

If the hashes differ, the script aborts rather than attempting an automatic rollback. This simple policy is conservative and appropriate for research data generation.

If this occurs, rebuild the database with:

```text
--reset_state_db
```

or implement a controlled rollback procedure before continuing.

## Missing dates

The indexer may not create a row in `daily_aggregates` for dates with no indexed activity. This is especially relevant during the earliest days of Bitcoin.

Metric exporters are responsible for applying the correct convention:

| Metric type | Missing date convention |
|---|---|
| Issuance | Export zero |
| Fees | Export zero |
| Miner revenue | Export zero |
| CDD | Export zero |
| Spent value | Export zero |
| Dormancy | Missing if spent value is zero |
| Fee-share ratio | Missing if issuance plus fees is zero |

This distinction is important. A zero value means the metric is defined and equal to zero. A missing value means the metric is undefined because its denominator is zero.

## Requirements

The indexer assumes:

- a synchronized Bitcoin Core full node;
- access to the Bitcoin Core JSON-RPC interface;
- historical block data;
- Python 3;
- SQLite through Python's standard library.

A non-pruned Bitcoin Core node is strongly recommended.

The indexer does not require:

- address clustering;
- entity identification;
- external price data;
- third-party APIs.

## Performance notes

This is the most computationally expensive OBM component because it resolves transaction inputs to previous outputs and maintains a live outpoint state.

Execution time depends on:

- disk speed;
- SQLite cache settings;
- Bitcoin Core RPC performance;
- CPU speed;
- the number of blocks processed;
- the `--commit_every` value.

For long historical builds, larger commit intervals such as:

```text
--commit_every 10000
```

may improve performance, at the cost of losing more progress if interrupted.

The database can become large because the `outpoints` table stores the live UTXO-like state required for future spent-output resolution. This table should not be pruned arbitrarily, because an old output can be spent later.

## Database maintenance

The `outpoints` table is essential and should not be pruned.

The `processed_blocks` table is useful for auditability and diagnostics. If database size becomes problematic, future versions may add a safe option to retain only recent `processed_blocks` rows.

After deleting rows from non-essential tables, SQLite disk space is not necessarily reclaimed until running:

```bash
sqlite3 cache/obm_spent_output_indexer.sqlite "VACUUM;"
```

Do not run `VACUUM` while the indexer is active.

## Validation

Recommended checks include:

- verify that `last_processed_height` increases monotonically;
- verify that `last_processed_hash` matches Bitcoin Core at the same height;
- inspect `duplicate_outpoints_overwritten`;
- inspect `negative_age_outputs_floored`;
- compare `coinbase_output_sats` with `issuance_sats + fees_sats`;
- compare exported `obm_fees_btc_daily` with `obm_miner_revenue_btc_daily - obm_issuance_btc_daily`;
- compare selected exported series with independent public data providers as diagnostics.

External comparisons should be interpreted cautiously because data providers may use different timestamp conventions, treatment of historical edge cases, or metric definitions.

## Export scripts

The indexer database is intended to be consumed by small export scripts, for example:

```text
export_obm_cdd_btcxdays_daily.py
export_obm_issuance_btc_daily.py
export_obm_fees_btc_daily.py
export_obm_miner_revenue_btc_daily.py
export_obm_spent_value_btc_daily.py
```

These scripts read the SQLite aggregate tables and write standard OBM CSV files with the usual schema:

```text
date,series_id,value,unit,frequency,release_version
```
