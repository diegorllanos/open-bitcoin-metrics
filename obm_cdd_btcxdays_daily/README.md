# Open Bitcoin Metrics: Bitcoin Days Destroyed

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_cdd_btcxdays_daily
```

The series reports daily **Bitcoin Days Destroyed (CDD)**, measured in BTC-days, exported from the persistent OBM spent-output indexer database.

The exporter script is:

```text
export_obm_cdd_btcxdays_daily.py
```

It reads the SQLite database generated by:

```text
obm_spent_output_indexer.py
```

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_cdd_btcxdays_daily` |
| Display name | Bitcoin Days Destroyed |
| Unit | `BTC-days` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Exported from `obm_spent_output_indexer.sqlite` |
| External data required | No |
| Main use | Coin-age activity, dormant-coin movement, UTXO-age analysis |

## Definition

Bitcoin Days Destroyed measures the value-weighted age of coins spent on a given day.

For each spent output `i`, let:

```text
ValueBTC_i
```

be the BTC value of the previous output being spent, and let:

```text
AgeDays_i
```

be the time, measured in days, between the creation of that previous output and the block in which it is spent.

The CDD contribution of spent output `i` is:

```text
CDD_i = ValueBTC_i * AgeDays_i
```

Daily Bitcoin Days Destroyed is the sum of these contributions over all outputs spent in blocks assigned to UTC calendar day `d`:

```text
CDD_d = sum_i ValueBTC_i * AgeDays_i
```

where the sum is taken over all spent outputs assigned to day `d`.

The unit is:

```text
BTC-days
```

For example, spending 2 BTC that have remained unspent for 100 days contributes:

```text
2 * 100 = 200 BTC-days
```

## Interpretation

`obm_cdd_btcxdays_daily` measures the destruction of accumulated coin age. It gives more weight to old coins than to recently moved coins.

This metric is useful for:

- identifying movement of long-dormant coins;
- studying whether old supply is becoming active;
- distinguishing high transaction activity from high old-coin movement;
- constructing derived metrics such as dormancy;
- analyzing long-term-holder behavior;
- studying coin-age dynamics around market cycles, halvings, or stress periods.

The metric should not be interpreted as transaction volume, payment volume, active users, or economic settlement value. A large CDD observation can result from a small number of old outputs moving, while a day with many transactions involving recently moved coins can have low CDD.

## Relationship with the spent-output indexer

This metric is exported from the table:

```text
daily_aggregates
```

in the SQLite database produced by:

```text
obm_spent_output_indexer.py
```

The relevant source column is:

```text
cdd_sats_days
```

The indexer stores CDD internally as satoshi-days:

```text
cdd_sats_days = sum(value_sats_i * age_days_i)
```

The exporter converts satoshi-days to BTC-days:

```text
value = cdd_sats_days / 100000000
```

The exporter does not query Bitcoin Core. It only reads the already generated indexer database and writes a standard OBM CSV file.

## Data format

The CSV file follows the standard OBM schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2024-01-01,obm_cdd_btcxdays_daily,3529142.48129384,BTC-days,daily,OBM v0.1.0
2024-01-02,obm_cdd_btcxdays_daily,2841277.91841720,BTC-days,daily,OBM v0.1.0
```

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_cdd_btcxdays_daily` |
| `value` | Daily Bitcoin Days Destroyed |
| `unit` | Measurement unit: `BTC-days` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version inherited from the indexer metadata |

## Reproducibility

The metric is generated by reading the persistent OBM spent-output indexer database.

For each date in the requested interval, the exporter:

1. opens the SQLite database generated by `obm_spent_output_indexer.py`;
2. verifies that the database metadata identify it as an OBM spent-output indexer database;
3. verifies that the requested ending date is not beyond the maximum processed date recorded by the indexer;
4. reads the `cdd_sats_days` value from `daily_aggregates`;
5. exports zero if a requested date has no row in `daily_aggregates`;
6. converts satoshi-days to BTC-days by dividing by 100,000,000;
7. writes the resulting time series to CSV using the standard OBM schema;
8. optionally generates a plot.

The blockchain scan, previous-output resolution, and age computation are performed by the shared spent-output indexer. This exporter is a deterministic transformation from the indexer database to the OBM CSV format.

## Typical script usage

Generate the CSV file:

```bash
python3 export_obm_cdd_btcxdays_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_cdd_btcxdays_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 export_obm_cdd_btcxdays_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_cdd_btcxdays_daily.csv \
  --plot \
  --plot_output figures/obm_cdd_btcxdays_daily.png
```

If `--plot_output` is omitted while `--plot` is used, the plot is saved next to the CSV file with a `.png` extension.

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--state_db` | Path to the SQLite database generated by `obm_spent_output_indexer.py` |
| `--output` | Output CSV file path |
| `--release_version` | Fallback release version if the indexer database does not contain one |
| `--plot` | Generate a plot of the exported series |
| `--plot_output` | Output path for the plot |

If the indexer database contains `release_version` metadata, the exporter uses that value. Otherwise, it uses the fallback value passed through `--release_version`.

## Requirements

The exporter assumes:

- an existing SQLite database generated by `obm_spent_output_indexer.py`;
- Python 3;
- SQLite through Python's standard library;
- `matplotlib`, only if plot generation is requested.

This exporter does not require:

- a running Bitcoin Core node;
- access to the Bitcoin Core JSON-RPC interface;
- direct block scanning;
- direct previous-output reconstruction at export time;
- address clustering;
- entity identification;
- external price data;
- third-party APIs.

The heavy blockchain processing is performed by the spent-output indexer before this exporter is run.

## Missing-date convention

If a requested date has no row in `daily_aggregates`, the exporter writes:

```text
0.00000000
```

for that date.

This convention is appropriate for CDD provided that the indexer database fully covers the requested interval. Under 
that condition, an absent daily aggregate row means that no relevant spent-output aggregate was assigned to that 
UTC date in the indexer database.

This differs from ratio metrics. For example, dormancy is computed as:

```text
CDD / spent value
```

and is undefined when spent value is zero. By contrast, CDD itself is a flow variable and can be equal to zero.

## Precision

The indexer stores CDD internally as a decimal satoshi-day value. The exporter converts this to BTC-days and writes values with eight decimal places:

```text
value = cdd_sats_days / 100000000
```

The eight-decimal output convention is consistent with BTC-denominated OBM series while preserving reproducible daily CDD values.

## Validation

The following internal checks are performed or recommended:

- verify that the indexer database was built from the Bitcoin genesis block onward, as assumed by OBM exporters;
- verify that `--start_date` is not later than `--end_date`;
- verify that the SQLite state database exists;
- verify that the database metadata contain the expected `indexer_id`;
- verify that the database contains processed-date metadata;
- verify that `--end_date` is not later than the maximum date processed by the indexer;
- verify that every requested date appears exactly once in the output;
- check that all exported values are non-negative;
- compare selected periods with previous OBM CDD exports or independent public data providers as diagnostics;
- verify that derived dormancy satisfies `dormancy = CDD / spent value` whenever spent value is positive.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, fractional-day treatment, historical duplicate-transaction handling, missing-date conventions, and the exact definition of transferred or spent value.

## Relationship with other OBM metrics

This metric is closely related to the following implemented or planned OBM metrics:

```text
obm_spent_value_btc_daily
obm_dormancy_days_daily
obm_cdd_per_supply_days_daily
obm_bincdd365d_btc_daily
```

The most important derived relationship is dormancy:

```text
obm_dormancy_days_daily =
    obm_cdd_btcxdays_daily / obm_spent_value_btc_daily
```

for dates where spent value is positive.

Another useful normalization is:

```text
obm_cdd_per_supply_days_daily =
    obm_cdd_btcxdays_daily / obm_supply_btc_daily
```

which expresses destroyed coin age per unit of supply.

## Indexer coverage assumption

The OBM spent-output indexer is designed to be built from the Bitcoin genesis block onward. Therefore, the exporter assumes that the indexer database contains a complete historical pass from block height 0 through the maximum processed height recorded in the metadata.

Under this invariant, a missing row in `daily_aggregates` for a requested date does not indicate an unprocessed date. It indicates that no spent-output aggregate was assigned to that UTC date under the indexer's timestamp convention. For `obm_cdd_btcxdays_daily`, such dates are therefore exported as zero.

Users should not use this exporter with a partially initialized or truncated indexer database unless they first verify that the requested date interval is fully covered.

## Known limitations

Take into account that this metric:

- is exported from the OBM spent-output indexer database;
- depends on the correctness and completeness of the indexer run;
- inherits the UTC block-timestamp convention of the indexer;
- is sensitive to the exact treatment of output age;
- floors negative apparent output ages to zero in the indexer;
- reflects spent-output age, not necessarily economic payment intent;
- can be dominated by a small number of old outputs;
- does not measure active users, entity-adjusted activity, transaction count, or fiat-denominated value;
- may differ from provider metrics that use different transferred-value definitions or timestamp conventions;
- may change if the underlying indexer definition or release version changes.

Despite these limitations, `obm_cdd_btcxdays_daily` is a core OBM series. It provides a transparent and reproducible measure of value-weighted coin-age destruction and supports research on dormant supply, long-term-holder behavior, and Bitcoin's monetary dynamics.
