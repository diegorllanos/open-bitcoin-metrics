# Open Bitcoin Metrics: Daily Spent Output Count

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_spent_output_count_daily
```

The series reports the daily number of previous outputs spent by non-coinbase transaction inputs. It is exported from the persistent OBM spent-output indexer database.

The exporter script is:

```text
export_obm_spent_output_count_daily.py
```

It reads the SQLite database generated by:

```text
obm_spent_output_indexer.py
```

The spent-output indexer itself is documented separately. This README focuses only on the metric-specific exporter.

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_spent_output_count_daily` |
| Display name | Daily spent output count |
| Unit | `outputs` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Exported from `obm_spent_output_indexer.sqlite` |
| External data required | No |
| Main use | UTXO-flow activity, input-side activity, spent-output analysis |

## Definition

`obm_spent_output_count_daily` measures the number of previous outputs spent by non-coinbase transaction inputs in blocks assigned to a given UTC calendar day.

For each non-coinbase transaction input, the indexer resolves the input to the previous output it spends. Each successfully spent previous output contributes one unit to the daily count.

The metric is defined as:

```text
SpentOutputCount_d = count_i(SpentOutput_i)
```

where the count is taken over all previous outputs spent by non-coinbase transaction inputs assigned to UTC calendar day `d`.

The unit is:

```text
outputs
```

## Interpretation

`obm_spent_output_count_daily` measures how many UTXOs are consumed on-chain each day.

This metric is useful for:

- measuring input-side transaction activity;
- analyzing UTXO turnover;
- complementing transaction-count metrics;
- studying wallet consolidation episodes;
- interpreting spent-value and coin-age metrics;
- constructing average spent value per spent output;
- supporting future age-band spent-output-count metrics.

This metric is different from transaction count. A single Bitcoin transaction can spend one input or many inputs. Therefore, transaction count measures the number of transactions, while spent output count measures the number of previous outputs consumed by those transactions.

The metric should not be interpreted as user count, payment count, entity-adjusted activity, or economically meaningful transfer count. It is a raw input-side count derived from the UTXO structure.

## Relationship with the spent-output indexer

This metric is exported from the table:

```text
daily_aggregates
```

in the SQLite database produced by:

```text
obm_spent_output_indexer.py
```

The relevant source column is:

```text
spent_output_count
```

The indexer stores the value directly as a daily count:

```text
spent_output_count = number of previous outputs spent by non-coinbase inputs
```

The exporter does not query Bitcoin Core. It only reads the already generated indexer database and writes a standard OBM CSV file.

## Data format

The CSV file follows the standard OBM schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2024-01-01,obm_spent_output_count_daily,752184,outputs,daily,OBM v0.1.0
2024-01-02,obm_spent_output_count_daily,681742,outputs,daily,OBM v0.1.0
```

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_spent_output_count_daily` |
| `value` | Number of spent previous outputs on that date |
| `unit` | Measurement unit: `outputs` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version inherited from the indexer metadata |

## Reproducibility

The metric is generated by reading the persistent OBM spent-output indexer database.

For each date in the requested interval, the exporter:

1. opens the SQLite database generated by `obm_spent_output_indexer.py`;
2. verifies that the database metadata identify it as an OBM spent-output indexer database;
3. verifies that the requested ending date is not beyond the maximum processed date recorded by the indexer;
4. reads the `spent_output_count` value from `daily_aggregates`;
5. exports zero if a requested date has no row in `daily_aggregates`;
6. writes the resulting time series to CSV using the standard OBM schema;
7. optionally generates a plot.

The blockchain scan and previous-output resolution are performed by the shared spent-output indexer. This exporter is a deterministic transformation from the indexer database to the OBM CSV format.

## Typical script usage

Generate the CSV file:

```bash
python3 export_obm_spent_output_count_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_spent_output_count_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 export_obm_spent_output_count_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_spent_output_count_daily.csv \
  --plot \
  --plot_output figures/obm_spent_output_count_daily.png
```

If `--plot_output` is omitted while `--plot` is used, the plot is saved next to the CSV file with a `.png` extension.

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--state_db` | Path to the SQLite database generated by `obm_spent_output_indexer.py` |
| `--output` | Output CSV file path |
| `--release_version` | Fallback release version if the indexer database does not contain one |
| `--plot` | Generate a plot of the exported series |
| `--plot_output` | Output path for the plot |

If the indexer database contains `release_version` metadata, the exporter uses that value. Otherwise, it uses the fallback value passed through `--release_version`.

## Requirements

The exporter assumes:

- an existing SQLite database generated by `obm_spent_output_indexer.py`;
- Python 3;
- SQLite through Python's standard library;
- `matplotlib`, only if plot generation is requested.

This exporter does not require:

- a running Bitcoin Core node;
- access to the Bitcoin Core JSON-RPC interface;
- direct block scanning;
- direct previous-output reconstruction at export time;
- address extraction;
- user clustering;
- entity identification;
- external price data;
- third-party APIs.

The heavy blockchain processing is performed by the spent-output indexer before this exporter is run.

## Missing-date convention

If a requested date has no row in `daily_aggregates`, the exporter writes:

```text
0
```

for that date.

This convention is appropriate because the metric is a daily count variable. If no spent-output aggregate is assigned to a UTC date under the indexer's timestamp convention, the number of spent outputs for that date is zero.

## Precision

The metric is an integer count. The exporter writes values without decimal places:

```text
value = spent_output_count
```

## Validation

Validation is divided into two groups: checks performed directly by the exporter script, and additional checks that are advisable for release preparation or independent auditing.

### Checks performed by the exporter

The exporter performs the following checks during execution:

- verifies that `--start_date` is not later than `--end_date`;
- verifies that the SQLite state database exists;
- opens the SQLite database in read-only mode;
- verifies that the database metadata contain the expected `indexer_id`;
- verifies that the database contains the required processing metadata, including `last_processed_height`, `last_processed_date`, and `max_processed_date`;
- verifies that the `daily_aggregates` table exists;
- verifies that the requested `--end_date` is not later than the maximum date processed by the indexer;
- iterates over every UTC date in the requested interval, ensuring that the output contains one row per calendar day;
- reads `spent_output_count` from `daily_aggregates` when a row exists for the date;
- writes zero when a requested date has no row in `daily_aggregates`;
- writes the output using the standard OBM schema.

These checks ensure that the exporter is reading from the expected indexer database, that the requested interval is covered by the indexer, and that the generated CSV has the expected daily structure.

### Recommended additional checks

The following checks are not performed automatically by the exporter, but are recommended before publishing a release or using the series in empirical work:

- verify that all exported values are non-negative integers;
- verify that every requested date appears exactly once in the output CSV;
- verify that `obm_spent_output_count_daily` is zero on dates where `obm_spent_value_btc_daily` is zero, provided both series are exported from the same indexer database and release version;
- verify that positive `obm_spent_value_btc_daily` normally coincides with positive `obm_spent_output_count_daily`;
- inspect unusually large daily spikes and confirm that they correspond to large input-count or consolidation episodes;
- compare selected periods with independently reconstructed input-count or spent-output-count series as diagnostics;
- check that the `release_version` field is consistent with the indexer metadata and with other OBM series generated from the same release;
- document any differences observed when comparing this metric with external providers.

A useful internal consistency relation is:

```text
obm_spent_output_count_daily = 0
    when obm_spent_value_btc_daily = 0
```

provided that both series are exported from the same indexer database and release version. The converse should usually hold under normal reconstruction, but should be interpreted cautiously if zero-value outputs are ever represented in the underlying data.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, transaction-input filtering, treatment of zero-value outputs, chain-reorganization handling, and historical edge-case handling.

## Relationship with other OBM metrics

This metric is closely related to:

```text
obm_spent_value_btc_daily
obm_cdd_btcxdays_daily
obm_dormancy_days_daily
obm_cdd_365d_btc_daily
```

It can be used to construct additional derived indicators, such as average spent value per spent output:

```text
obm_spent_value_btc_daily / obm_spent_output_count_daily
```

for dates where the spent-output count is positive.

It is also useful for interpreting CDD and dormancy spikes. A large CDD value generated by a small spent-output count may indicate movement of a small number of old or large outputs, while a large spent-output count with moderate CDD may indicate broad but relatively young output turnover.

## Known limitations

Take into account that this metric:

- is exported from the OBM spent-output indexer database;
- depends on the correctness and completeness of the indexer run;
- inherits the UTC block-timestamp convention of the indexer;
- is a raw spent-output count, not an entity-adjusted activity measure;
- counts previous outputs consumed by transaction inputs, not transactions;
- does not identify users, entities, exchanges, custodians, or payment purpose;
- can be affected by wallet consolidation, batching, exchange operations, self-transfers, and custodial wallet management;
- does not measure BTC value, fiat value, transaction fees, or coin age;
- may change if the underlying indexer definition or release version changes.

Despite these limitations, `obm_spent_output_count_daily` is a useful OBM activity series. It provides a transparent raw count of outputs consumed on-chain and complements transaction count, spent value, CDD, dormancy, and age-threshold metrics in the study of UTXO-flow dynamics.
