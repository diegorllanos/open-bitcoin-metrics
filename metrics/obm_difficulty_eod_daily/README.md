# Open Bitcoin Metrics: End-of-Day Bitcoin Mining Difficulty

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_difficulty_eod_daily
```

The series reports the Bitcoin mining difficulty of the last block assigned to each UTC calendar day. The unit field 
is recorded as difficulty. Unlike other OBM metrics, the unit is not repeated in the series identifier because 
"difficulty" is itself the named Bitcoin protocol state variable being measured.

The computation script is:

```text
compute_obm_difficulty_eod_daily.py
```

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_difficulty_eod_daily` |
| Display name | End-of-day Bitcoin mining difficulty |
| Unit | `difficulty` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Direct Bitcoin Core block scan |
| External data required | No |
| Main use | Mining conditions, protocol state, difficulty-retarget analysis, hashrate-related studies |

## Definition

`obm_difficulty_eod_daily` measures the Bitcoin mining difficulty observed at the end of each UTC calendar day, under the OBM block-timestamp convention.

Let `B_d` denote the set of blocks assigned to UTC date `d`. For each block `b`, let:

```text
height_b
```

be the block height, and let:

```text
Difficulty_b
```

be the mining difficulty reported by Bitcoin Core for that block.

The metric is defined as:

```text
DifficultyEOD_d =
    Difficulty_b*
```

where:

```text
b* = argmax_{b in B_d} height_b
```

That is, `b*` is the highest-height block among all blocks assigned to UTC date `d`.

A block is assigned to a UTC calendar date using its block timestamp as returned by Bitcoin Core:

```text
d(b) = UTCDate(block_time_b)
```

If no block is assigned to date `d`, the value is undefined and is written as:

```text
NaN
```

The standard OBM daily calendar starts on `2009-01-01`; release exports should not use 
earlier `--start_date` values.

## Why end-of-day difficulty?

Difficulty is a protocol state variable, not a daily flow. It should not be summed across blocks or across days.

The end-of-day convention treats the metric as a stock-like variable:

```text
obm_difficulty_eod_daily =
    difficulty of the highest-height block assigned to UTC date d
```

This is analogous to using an end-of-period observation for a financial, monetary, or protocol state variable.

An alternative would be an average daily difficulty across blocks assigned to a date, but that would be less natural for a stepwise protocol variable. Difficulty remains constant during a difficulty epoch and changes only at retarget boundaries. The end-of-day convention records the difficulty state reached by the end of the UTC date.

## Interpretation

Bitcoin mining difficulty is the relative difficulty of producing a valid block under the proof-of-work target, compared with Bitcoin's reference difficulty. It adjusts periodically so that Bitcoin continues to target an average inter-block interval of approximately ten minutes.

`obm_difficulty_eod_daily` is useful for:

- studying mining conditions;
- analyzing difficulty retargets;
- complementing block count and block weight;
- supporting mining and energy-related empirical studies;
- constructing difficulty-based hashrate estimates;
- controlling for protocol mining conditions in econometric models.

The metric should not be interpreted as observed hashrate. Difficulty is an on-chain protocol state variable, whereas hashrate is inferred from difficulty and realized block production over a chosen time window.

## Data source and input requirements

The metric is computed directly from a running Bitcoin Core full node through the JSON-RPC interface.

For each block in the selected interval, the script retrieves the decoded block using:

```text
getblock <block_hash> 1
```

The script reads the block-level `difficulty` field returned by Bitcoin Core.

This metric requires:

- a synchronized Bitcoin Core full node;
- JSON-RPC access to the node;
- access to decoded block metadata.

This metric does not require:

- the OBM spent-output indexer database;
- `txindex=1`;
- previous-output reconstruction;
- transaction-level scanning;
- address extraction;
- user clustering;
- entity identification;
- external price data;
- third-party APIs.

Although `txindex=1` is useful for other OBM metrics, it is not required here because the metric uses only block-level metadata.

## Reproducibility

The metric is generated by scanning blocks in a date interval and selecting, for each UTC date, the difficulty of the highest-height block assigned to that date.

For each selected date interval, the script:

1. connects to Bitcoin Core through JSON-RPC;
2. obtains the current chain tip using `getblockchaininfo`;
3. identifies an approximate block-height interval covering the requested UTC dates;
4. expands the interval using `--height_margin`;
5. scans every block in the expanded interval;
6. assigns each block to a UTC calendar date using the block timestamp;
7. skips blocks outside the requested date interval;
8. reads each counted block's `difficulty` field;
9. keeps the difficulty of the highest-height block assigned to each UTC date;
10. writes `NaN` for selected dates with no assigned block;
11. writes one row per UTC date using the standard OBM schema;
12. optionally generates a plot.

The height-margin expansion is used because Bitcoin block timestamps are not strictly monotonic with respect to block height. The expanded scan interval reduces the risk of missing boundary blocks whose timestamps fall inside the selected UTC dates.

## Typical script usage

Generate the CSV file using Bitcoin Core cookie authentication:

```bash
python3 compute_obm_difficulty_eod_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --use_default_cookie \
  --output data/daily/obm_difficulty_eod_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 compute_obm_difficulty_eod_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --use_default_cookie \
  --output data/daily/obm_difficulty_eod_daily.csv \
  --plot \
  --plot_output figures/obm_difficulty_eod_daily.png
```

When plotting is requested, `NaN` observations are skipped. If the selected interval contains no defined difficulty observations, the plotting step fails because there is no defined series to display.

Generate the CSV file using explicit RPC credentials:

```bash
python3 compute_obm_difficulty_eod_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --rpc_url http://127.0.0.1:8332 \
  --rpc_user my_rpc_user \
  --rpc_password my_rpc_password \
  --output data/daily/obm_difficulty_eod_daily.csv
```

RPC credentials can also be supplied through environment variables:

```bash
export BITCOIN_RPC_URL="http://127.0.0.1:8332"
export BITCOIN_RPC_USER="my_rpc_user"
export BITCOIN_RPC_PASSWORD="my_rpc_password"
```

Then run:

```bash
python3 compute_obm_difficulty_eod_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --output data/daily/obm_difficulty_eod_daily.csv
```

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--rpc_url` | Bitcoin Core RPC URL |
| `--rpc_user` | Bitcoin Core RPC username |
| `--rpc_password` | Bitcoin Core RPC password |
| `--cookie_path` | Path to Bitcoin Core RPC cookie file |
| `--use_default_cookie` | Use the default cookie path `~/.bitcoin/.cookie` |
| `--rpc_timeout` | RPC timeout in seconds |
| `--height_margin` | Extra blocks scanned before and after the approximate height interval |
| `--output` | Output CSV file path |
| `--release_version` | Dataset release version written to the output |
| `--plot` | Generate a plot of the resulting series |
| `--plot_output` | Output path for the plot |
| `--quiet` | Suppress diagnostic messages printed to standard error |

The default output file is:

```text
obm_difficulty_eod_daily.csv
```

The default release version is:

```text
OBM v0.1.0
```

The default height margin is:

```text
288 blocks
```

This corresponds to approximately two days of expected Bitcoin block production.

## Data format

The output CSV file follows the standard OBM scalar schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2009-01-03,obm_difficulty_eod_daily,1.000000000000,difficulty,daily,OBM v0.1.0
2009-01-04,obm_difficulty_eod_daily,NaN,difficulty,daily,OBM v0.1.0
2024-01-01,obm_difficulty_eod_daily,73197634206448.906250000000,difficulty,daily,OBM v0.1.0
```

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_difficulty_eod_daily` |
| `value` | Difficulty of the highest-height block assigned to the UTC date, or `NaN` |
| `unit` | Measurement unit: `difficulty` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version |

## Missing-date convention

Difficulty is a state variable, but this series is defined as the difficulty of the last block assigned to each UTC date.  If the selected UTC date lies within the historical interval covered by the local node and no block is assigned to that date, the script writes:

```text
NaN
```

This is preferable to zero because zero would be economically and technically misleading. Dates beyond the current chain tip should not be exported as NaN, because they are unavailable future observations rather than historical no-block dates.

A missing value means that the end-of-day observation is undefined under the selected block-timestamp convention.

Users who require a fully filled state series may forward-fill `obm_difficulty_eod_daily` after export, but such forward-filling is a downstream transformation and is not performed by this script.

## Precision

Bitcoin Core returns difficulty as a JSON numeric value. The script parses this value using Python's `Decimal` type and writes defined observations with twelve decimal places.

Difficulty is a dimensionless relative measure, but the output unit field is recorded as:

```text
difficulty
```

because this is more informative than simply writing `dimensionless`.

## Validation

Validation is divided into two groups: checks performed directly by the script, and additional checks that are advisable for release preparation or independent auditing.

### Checks performed by the script

The script performs the following checks during execution:

- verifies that `--start_date` is not later than `--end_date`;
- verifies that `--height_margin` is non-negative;
- verifies that the RPC authentication configuration is valid;
- verifies that the RPC cookie file exists and has valid format when cookie authentication is used;
- connects to Bitcoin Core through JSON-RPC;
- obtains the current chain tip using `getblockchaininfo`;
- locates an approximate block-height interval for the requested timestamp range;
- expands the scan interval using `--height_margin`;
- scans all blocks in the expanded interval;
- assigns each scanned block to a UTC date using the block timestamp;
- counts only blocks whose UTC date lies inside the requested interval;
- verifies that each counted block contains a `difficulty` field;
- rejects negative difficulty values;
- selects the highest-height block assigned to each UTC date;
- writes `NaN` for selected dates with no assigned block;
- writes one output row per selected UTC date;
- writes the output using the standard OBM schema;
- optionally generates a plot when `--plot` is used;
- prints diagnostics including counted blocks, scanned blocks, defined observations, and `NaN` observations, unless `--quiet` is used.

These checks ensure that the script scans a sufficiently broad block interval, uses the block-level difficulty field, preserves one row per selected date, and applies the end-of-day convention consistently.

### Recommended additional checks

The following checks are not performed automatically by the script, but are recommended before publishing a release or using the series in empirical work:

- verify that every requested date appears exactly once in the output CSV;
- verify that all defined values are positive;
- verify that early dates with no blocks are recorded as `NaN`, not zero;
- verify that difficulty remains constant within ordinary retarget periods and changes at difficulty-adjustment boundaries;
- compare selected retarget dates with independent Bitcoin block explorers or data providers;
- compare the number of defined observations with `obm_block_count_daily`: dates with positive block count should have defined difficulty values;
- verify that `NaN` values occur only on dates with zero block count under the same UTC timestamp convention;
- inspect unusually large changes and confirm that they coincide with retarget boundaries;
- document any differences observed when comparing with external difficulty series.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, daily boundary rules, whether they report end-of-day difficulty, average difficulty, or forward-filled difficulty, and how they handle dates with no blocks.

## Relationship with other OBM metrics

This metric is closely related to:

```text
obm_block_count_daily
obm_block_weight_wu_daily
obm_fees_btc_daily
```

The relationship with block count is particularly important. If `obm_block_count_daily` is positive for date `d`, then `obm_difficulty_eod_daily` should normally be defined for that date. If block count is zero, the end-of-day difficulty observation is undefined under the OBM convention and is written as `NaN`.

Difficulty can also be used as an input for estimated hashrate metrics. However, hashrate is not directly observed on-chain and requires an estimation window and additional assumptions. Therefore, `obm_difficulty_eod_daily` should be treated as a protocol state variable, not as a direct hashrate measure.

## Aggregation to lower frequencies

Because difficulty is a protocol state variable, a monthly version should normally use an end-of-period convention, such as the difficulty of the highest-height block assigned to the last UTC date of the month with an assigned block. A monthly average can be constructed for specific empirical purposes, but it should be documented as a separate convention.

## Known limitations

Take into account that this metric:

- reports end-of-day difficulty, not average daily difficulty;
- is defined using the highest-height block assigned to each UTC date;
- writes `NaN` for dates with no assigned block;
- depends on the block timestamp convention used to assign blocks to UTC dates;
- is a protocol state variable, not a flow;
- does not directly measure hashrate;
- does not directly measure mining profitability;
- does not directly measure transaction demand, network usage, or economic activity;
- is directly computed from decoded block metadata and does not require the spent-output indexer;
- may differ from provider series that forward-fill difficulty or report average daily difficulty.

Despite these limitations, `obm_difficulty_eod_daily` is a useful OBM protocol-state series. It provides a transparent, full-node-derived measure of Bitcoin mining difficulty and complements block count, block weight, fees, miner revenue, and future estimated-hashrate metrics.
