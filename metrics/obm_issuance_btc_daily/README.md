# Open Bitcoin Metrics: Daily Bitcoin Issuance

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_issuance_btc_daily
```

The series reports daily realized Bitcoin issuance, measured in BTC, exported from the persistent OBM spent-output indexer database.

The exporter script is:

```text
export_obm_issuance_btc_daily.py
```

It reads the SQLite database generated by:

```text
obm_spent_output_indexer.py
```

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_issuance_btc_daily` |
| Display name | Daily Bitcoin issuance |
| Unit | `BTC` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Exported from `obm_spent_output_indexer.sqlite` |
| External data required | No |
| Main use | Monetary issuance, subsidy dynamics, supply-growth analysis |

## Definition

Let `B_d` denote the set of Bitcoin blocks assigned to UTC calendar day `d`. For each block `b`, let:

```text
CoinbaseOutput_b
```

denote the total output value of the coinbase transaction in that block, measured in BTC, and let:

```text
Fees_b
```

denote the total transaction fees paid by non-coinbase transactions in that block, also measured in BTC.

Realized issuance in block `b` is defined as:

```text
Issuance_b = CoinbaseOutput_b - Fees_b
```

Daily realized issuance is then:

```text
Issuance_d = sum_{b in B_d} Issuance_b
```

A block is assigned to a day according to the UTC date derived from the block timestamp returned by Bitcoin Core.

This definition separates newly issued BTC from transaction fees. The coinbase transaction pays miners both newly issued BTC and transaction fees, but fees are transfers of already existing BTC. Therefore, the newly issued component is obtained by subtracting transaction fees from the total coinbase output value.

## Interpretation

`obm_issuance_btc_daily` measures how many new bitcoins were created on each UTC calendar day under OBM's block-timestamp convention.

This metric is useful for:

- studying Bitcoin's realized monetary issuance;
- measuring daily supply expansion;
- analyzing subsidy reductions around halving events;
- constructing cumulative supply series such as `obm_supply_btc_daily`;
- separating the issuance and fee components of miner compensation;
- building econometric datasets involving Bitcoin supply and monetary growth.

The series should not be confused with miner revenue. Miner revenue includes both newly issued BTC and transaction fees:

```text
MinerRevenueBTC_d = Issuance_d + FeesBTC_d
```

By contrast, this series isolates only the newly issued BTC component.

## Relationship with the spent-output indexer

This metric is exported from the table:

```text
daily_aggregates
```

in the SQLite database produced by:

```text
obm_spent_output_indexer.py
```

The relevant source column is:

```text
issuance_sats
```

The exporter converts satoshis to BTC:

```text
value = issuance_sats / 100000000
```

The indexer computes:

```text
issuance_sats = coinbase_output_sats - fees_sats
```

where:

- `coinbase_output_sats` is the total value of the coinbase transaction outputs, in satoshis;
- `fees_sats` is the total transaction fees paid by non-coinbase transactions, in satoshis.

The exporter does not query Bitcoin Core. It only reads the already generated indexer database and writes a standard OBM CSV file.

## Indexer coverage assumption

The OBM spent-output indexer is designed to be built from the Bitcoin genesis block onward. Therefore, this exporter assumes that the 
indexer database contains a complete historical pass from block height 0 through the maximum processed height recorded in the metadata.

Under this invariant, a missing row in `daily_aggregates` for a requested UTC date does not indicate an unprocessed date. It indicates 
that no block-level aggregate activity was assigned to that date under the indexer's timestamp convention. For `obm_issuance_btc_daily`, 
such dates are therefore exported as zero.

Users should not use this exporter with a partially initialized or truncated indexer database unless they first verify that the 
requested date interval is fully covered.

## Data format

The CSV file follows the standard OBM schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2024-01-01,obm_issuance_btc_daily,918.75000000,BTC,daily,OBM v0.1.0
2024-01-02,obm_issuance_btc_daily,881.25000000,BTC,daily,OBM v0.1.0
```

## Precision

The exporter writes the `value` field with eight decimal places:

```text
value = issuance_sats / 100000000
```

This matches the BTC-denominated precision convention used by other OBM series.

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_issuance_btc_daily` |
| `value` | Daily realized Bitcoin issuance |
| `unit` | Measurement unit: `BTC` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version inherited from the indexer metadata |

## Reproducibility

The metric is generated by reading the persistent OBM spent-output indexer database.

For each date in the requested interval, the exporter:

1. opens the SQLite database generated by `obm_spent_output_indexer.py`;
2. verifies that the database metadata identify it as an OBM spent-output indexer database;
3. verifies that the requested ending date is not beyond the maximum processed date recorded by the indexer;
4. reads the `issuance_sats` value from `daily_aggregates`;
5. exports zero if a requested date has no row in `daily_aggregates`;
6. converts satoshis to BTC by dividing by 100,000,000;
7. writes the resulting time series to CSV using the standard OBM schema;
8. optionally generates a plot.

Unlike earlier standalone scripts, this exporter does not scan blocks directly and does not connect to Bitcoin Core. The blockchain scan is performed once by the shared spent-output indexer.

## Typical script usage

Generate the CSV file:

```bash
python3 export_obm_issuance_btc_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_issuance_btc_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 export_obm_issuance_btc_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_issuance_btc_daily.csv \
  --plot \
  --plot_output figures/obm_issuance_btc_daily.png
```

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--state_db` | Path to the SQLite database generated by `obm_spent_output_indexer.py` |
| `--output` | Output CSV file path |
| `--release_version` | Fallback release version if the indexer database does not contain one |
| `--plot` | Generate a plot of the exported series |
| `--plot_output` | Output path for the plot |

If the indexer database contains `release_version` metadata, the exporter uses that value. Otherwise, it uses the fallback value passed through `--release_version`.

## Requirements

The exporter assumes:

- an existing SQLite database generated by `obm_spent_output_indexer.py`;
- Python 3;
- SQLite through Python's standard library;
- `matplotlib`, only if plot generation is requested.

This exporter does not require:

- a running Bitcoin Core node;
- access to the Bitcoin Core JSON-RPC interface;
- direct block scanning;
- transaction-level parsing;
- previous-output reconstruction;
- external price data;
- third-party APIs.

The heavy blockchain processing is performed by the spent-output indexer before this exporter is run.

## Missing-date convention

If a requested date has no row in `daily_aggregates`, the exporter writes:

```text
0.00000000
```

for that date.

This convention is appropriate for issuance because an absent aggregate row means that the indexer observed no block-level aggregate activity assigned to that UTC date. In the earliest days of Bitcoin, there may be UTC dates with no blocks assigned under the block-timestamp convention. For such dates, realized issuance is zero.

## Validation

The exporter performs several structural checks, and additional validation checks are recommended:

The exporter checks that:

- the SQLite state database exists;
- the database metadata contain the expected `indexer_id`;
- the database contains processed-date metadata;
- the `daily_aggregates` table is present;
- `--end_date` is not later than the maximum date processed by the indexer.

Additional validation checks include:

- verify that every requested date appears exactly once in the output;
- verify that output values are non-negative BTC amounts under normal issuance conditions;
- check that values drop around subsidy halving periods;
- verify that first differences of `obm_supply_btc_daily` reproduce this series;
- compare this series with the difference between miner revenue and fees;
- compare selected periods with independent public Bitcoin data providers as diagnostics.

The most important consistency relation is:

```text
obm_issuance_btc_daily =
    obm_miner_revenue_btc_daily - obm_fees_btc_daily
```

provided that all three series are exported from the same indexer database, using the same timestamp convention and release version.

Another important relation is:

```text
obm_miner_revenue_btc_daily =
    obm_issuance_btc_daily + obm_fees_btc_daily
```

up to exact decimal representation.

## Aggregation to lower frequencies

Because issuance is a flow variable, monthly issuance should be computed as the sum of the corresponding daily issuance values:

```text
Issuance_m = sum of Issuance_d over all days d in month m
```

It should not be computed as an average of daily issuance values unless the research question specifically requires 
an average daily issuance rate.

## Known limitations

Take into account that this metric:

- is exported from the OBM spent-output indexer database;
- depends on the correctness and completeness of the indexer run;
- inherits the UTC block-timestamp convention of the indexer;
- reports realized issuance by block assignment date, not wall-clock monetary policy schedule;
- does not include transaction fees;
- does not measure miner revenue;
- is denominated in BTC, not in fiat currency;
- may change if the underlying indexer definition or release version changes.

Despite these limitations, `obm_issuance_btc_daily` is a core OBM series. It provides a transparent measure of Bitcoin's realized monetary issuance and is a building block for supply, miner-revenue, fee-share, and monetary-growth analyses.
