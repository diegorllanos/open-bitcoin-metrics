# Open Bitcoin Metrics: 365-Day CDD Threshold Spent Value in BTC

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_spent_value_ge365_btc_daily
```

The series reports the total daily BTC value of outputs spent after remaining unspent for at least 365 days. It is exported from the persistent OBM spent-output indexer database.

The exporter script is:

```text
export_obm_spent_value_ge365_btc_daily.py
```

It reads the SQLite database generated by:

```text
obm_spent_output_indexer.py
```

The spent-output indexer itself is documented separately. This README focuses only on the metric-specific exporter.

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_spent_value_ge365_btc_daily` |
| Display name | 365-day CDD threshold spent value in BTC |
| Unit | `BTC` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Exported from `obm_spent_output_indexer.sqlite` |
| External data required | No |
| Main use | Long-dormant spent value, coin-age activity, long-term-holder behavior |

## Definition

`obm_spent_value_ge365_btc_daily` measures the BTC value of outputs spent on a given UTC calendar day whose age is at least 365 days.

For each spent output `i`, let:

```text
ValueBTC_i
```

be the BTC value of the previous output being spent, and let:

```text
AgeDays_i
```

be the age of that previous output, measured as the elapsed time in days between the block in which the output was created and the block in which it is spent.

The metric is defined as:

```text
CDD365BTC_d = sum_i ValueBTC_i * 1{AgeDays_i >= 365}
```

where the sum is taken over all spent outputs assigned to UTC calendar day `d`.

The unit is:

```text
BTC
```

This is important. Although the series belongs to the CDD family of coin-age metrics, it is not measured in BTC-days. It is a binary-threshold spent-value metric: each spent output either contributes its full BTC value if its age is at least 365 days, or contributes zero otherwise.

## Interpretation

`obm_spent_value_ge365_btc_daily` measures how much BTC value was spent after at least one year of inactivity.

This metric is useful for:

- identifying movement of long-dormant coins;
- measuring the BTC value of spent outputs with age at least 365 days;
- studying long-term-holder activity;
- complementing raw Bitcoin Days Destroyed;
- distinguishing old-coin movement from recently active turnover;
- constructing long-term-holder spent-value ratios and related age-threshold metrics.

For example, if a day includes the following spent outputs:

```text
2 BTC aged 100 days
1 BTC aged 400 days
3 BTC aged 800 days
```

then:

```text
obm_spent_value_ge365_btc_daily = 1 + 3 = 4 BTC
```

The 2 BTC output aged 100 days does not contribute because its age is below the 365-day threshold.

The metric should not be interpreted as conventional Bitcoin Days Destroyed. Conventional CDD multiplies value by age and is measured in BTC-days. This metric uses age only as a binary threshold and is measured in BTC.

## Relationship with the spent-output indexer

This metric is exported from the table:

```text
daily_aggregates
```

in the SQLite database produced by:

```text
obm_spent_output_indexer.py
```

The relevant source column is:

```text
spent_value_365d_sats
```

The indexer stores the value internally as satoshis:

```text
spent_value_365d_sats = sum(value_sats_i for outputs with age_days_i >= 365)
```

The exporter converts satoshis to BTC:

```text
value = spent_value_365d_sats / 100000000
```

The exporter does not query Bitcoin Core. It only reads the already generated indexer database and writes a standard OBM CSV file.

## Data format

The CSV file follows the standard OBM schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2024-01-01,obm_spent_value_ge365_btc_daily,34182.49281735,BTC,daily,OBM v0.1.0
2024-01-02,obm_spent_value_ge365_btc_daily,29104.18290472,BTC,daily,OBM v0.1.0
```

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_spent_value_ge365_btc_daily` |
| `value` | Total BTC value of spent outputs aged at least 365 days |
| `unit` | Measurement unit: `BTC` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version inherited from the indexer metadata |

## Reproducibility

The metric is generated by reading the persistent OBM spent-output indexer database.

For each date in the requested interval, the exporter:

1. opens the SQLite database generated by `obm_spent_output_indexer.py`;
2. verifies that the database metadata identify it as an OBM spent-output indexer database;
3. verifies that the requested ending date is not beyond the maximum processed date recorded by the indexer;
4. reads the `spent_value_365d_sats` value from `daily_aggregates`;
5. exports zero if a requested date has no row in `daily_aggregates`;
6. converts satoshis to BTC by dividing by 100,000,000;
7. writes the resulting time series to CSV using the standard OBM schema;
8. optionally generates a plot.

The blockchain scan, previous-output resolution, and output-age computation are performed by the shared spent-output indexer. This exporter is a deterministic transformation from the indexer database to the OBM CSV format.

## Typical script usage

Generate the CSV file:

```bash
python3 export_obm_spent_value_ge365_btc_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_spent_value_ge365_btc_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 export_obm_spent_value_ge365_btc_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_spent_value_ge365_btc_daily.csv \
  --plot \
  --plot_output figures/obm_spent_value_ge365_btc_daily.png
```

If `--plot_output` is omitted while `--plot` is used, the plot is saved next to the CSV file with a `.png` extension.

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--state_db` | Path to the SQLite database generated by `obm_spent_output_indexer.py` |
| `--output` | Output CSV file path |
| `--release_version` | Fallback release version if the indexer database does not contain one |
| `--plot` | Generate a plot of the exported series |
| `--plot_output` | Output path for the plot |

If the indexer database contains `release_version` metadata, the exporter uses that value. Otherwise, it uses the fallback value passed through `--release_version`.

## Requirements

The exporter assumes:

- an existing SQLite database generated by `obm_spent_output_indexer.py`;
- Python 3;
- SQLite through Python's standard library;
- `matplotlib`, only if plot generation is requested.

This exporter does not require:

- a running Bitcoin Core node;
- access to the Bitcoin Core JSON-RPC interface;
- direct block scanning;
- direct previous-output reconstruction at export time;
- address extraction;
- user clustering;
- entity identification;
- external price data;
- third-party APIs.

The heavy blockchain processing is performed by the spent-output indexer before this exporter is run.

## Missing-date convention

If a requested date has no row in `daily_aggregates`, the exporter writes:

```text
0.00000000
```

for that date.

This convention is appropriate because the metric is a daily flow variable. If no qualifying spent-output aggregate is assigned to a UTC date under the indexer's timestamp convention, the total BTC value of spent outputs aged at least 365 days is zero.

## Precision

The indexer stores qualifying spent output values internally as integer satoshis. The exporter converts this value to BTC and writes values with eight decimal places:

```text
value = spent_value_365d_sats / 100000000
```

This preserves the standard Bitcoin monetary precision.

## Validation

Validation is divided into two groups: checks performed directly by the exporter script, and additional checks that are advisable for release preparation or independent auditing.

### Checks performed by the exporter

The exporter performs the following checks during execution:

- verifies that `--start_date` is not later than `--end_date`;
- verifies that the SQLite state database exists;
- opens the SQLite database in read-only mode;
- verifies that the database metadata contain the expected `indexer_id`;
- verifies that the database contains the required processing metadata, including `last_processed_height`, `last_processed_date`, and `max_processed_date`;
- verifies that the `daily_aggregates` table exists;
- verifies that the requested `--end_date` is not later than the maximum date processed by the indexer;
- iterates over every UTC date in the requested interval, ensuring that the output contains one row per calendar day;
- reads `spent_value_365d_sats` from `daily_aggregates` when a row exists for the date;
- writes zero when a requested date has no row in `daily_aggregates`;
- converts satoshis to BTC by dividing by 100,000,000;
- writes the output using the standard OBM schema.

These checks ensure that the exporter is reading from the expected indexer database, that the requested interval is covered by the indexer, and that the generated CSV has the expected daily structure.

### Recommended additional checks

The following checks are not performed automatically by the exporter, but are recommended before publishing a release or using the series in empirical work:

- verify that all exported values are non-negative;
- verify that every requested date appears exactly once in the output CSV;
- verify that `obm_spent_value_ge365_btc_daily <= obm_spent_value_btc_daily` for every date when both series are exported from the same indexer database and release version;
- verify that the first non-zero observations occur only after outputs can plausibly have reached the 365-day age threshold;
- inspect unusually large daily spikes and confirm that they correspond to large old-output movements;
- compare selected periods with independent long-term-holder spent-value, old-coin movement, or age-threshold metrics as diagnostics;
- check that the `release_version` field is consistent with the indexer metadata and with other OBM series generated from the same release;
- document any differences observed when comparing this metric with external providers.

A useful internal consistency relation is:

```text
0 <= obm_spent_value_ge365_btc_daily <= obm_spent_value_btc_daily
```

for every UTC date, provided that both series are exported from the same indexer database and release version.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, output-age thresholding, entity adjustment, change-output treatment, transfer-value definition, and historical edge-case handling.


## Relationship with other OBM metrics

This metric is closely related to:

```text
obm_cdd_btcxdays_daily
obm_spent_value_btc_daily
obm_dormancy_days_daily
```

The relationship with raw CDD is conceptual rather than algebraic. Raw CDD is measured in BTC-days:

```text
obm_cdd_btcxdays_daily = sum(ValueBTC_i * AgeDays_i)
```

whereas this metric is measured in BTC:

```text
obm_spent_value_ge365_btc_daily = sum(ValueBTC_i * 1{AgeDays_i >= 365})
```

The relationship with spent value is bounded:

```text
obm_spent_value_ge365_btc_daily <= obm_spent_value_btc_daily
```

because the 365-day threshold series is a subset of total spent value.

The metric can also support derived ratios, such as the share of spent value coming from outputs aged at least 365 days:

```text
obm_spent_value_ge365_btc_daily / obm_spent_value_btc_daily
```

for dates where total spent value is positive.

## Known limitations

Take into account that this metric:

- is exported from the OBM spent-output indexer database;
- depends on the correctness and completeness of the indexer run;
- inherits the UTC block-timestamp convention of the indexer;
- inherits the fractional-day age convention used by the indexer;
- uses a sharp 365-day threshold;
- is a raw spent-output metric, not an entity-adjusted measure;
- includes self-transfers, change-related activity, batching, and consolidation transactions;
- does not identify users, entities, exchanges, custodians, or payment purpose;
- is measured in BTC, not BTC-days;
- may change if the underlying indexer definition or release version changes.

Despite these limitations, `obm_spent_value_ge365_btc_daily` is a useful OBM coin-age threshold series. It provides a transparent measure of the BTC value of outputs spent after at least one year of inactivity and complements raw CDD, dormancy, spent-value, and long-term-holder activity indicators.
