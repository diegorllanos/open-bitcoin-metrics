# Open Bitcoin Metrics: Daily Bitcoin Days Destroyed by Age Band

This repository provides the following wide daily table of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_cdd_age_band_btcxdays_daily
```

The table reports daily Bitcoin Days Destroyed (CDD) split by output-age band. It is exported from the persistent OBM spent-output indexer database.

The exporter script is:

```text
export_obm_cdd_age_band_btcxdays_daily.py
```

A standalone plotting utility is also available:

```text
plot_obm_cdd_age_band_btcxdays_daily.py
```

The exporter reads the SQLite database generated by:

```text
obm_spent_output_indexer.py
```

The spent-output indexer itself is documented separately. This README focuses only on the metric-specific exporter and its output table.

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_cdd_age_band_btcxdays_daily` |
| Display name | Daily Bitcoin Days Destroyed by age band |
| Unit | `BTC-days` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Exported from `obm_spent_output_indexer.sqlite` |
| External data required | No |
| Output shape | Wide table, one row per date, one column per age band |
| Main use | CDD age decomposition, dormant-supply analysis, validation of aggregate CDD |

## Definition

`obm_cdd_age_band_btcxdays_daily` decomposes daily Bitcoin Days Destroyed by the age of the outputs at the moment they are spent.

For each spent output `i`, let:

```text
ValueBTC_i
```

be the BTC value of the previous output being spent, and let:

```text
AgeDays_i
```

be the age of that previous output, measured as the elapsed time in days between the block in which the output was created and the block in which it is spent.

For each UTC day `d` and age band `k`, the metric reports:

```text
CDDAgeBandBTCxDays_{d,k}
    = sum_i ValueBTC_i * AgeDays_i * 1{AgeDays_i belongs to band k}
```

where the sum is taken over all outputs spent in blocks assigned to UTC calendar day `d`.

The unit is:

```text
BTC-days
```

This metric is not a scalar daily series. It is a wide daily age-band table: each row corresponds to one UTC date, and each age-band column contains the CDD contributed by outputs assigned to that band.

The standard OBM daily calendar starts on `2009-01-01`; release exports should not use 
earlier `--start_date` values.

The exporter uses the following fixed age bands:

| Age-band label | Output column |
|---|---|
| `0d_1d` | `cdd_0d_1d_btcxdays` |
| `1d_1w` | `cdd_1d_1w_btcxdays` |
| `1w_1m` | `cdd_1w_1m_btcxdays` |
| `1m_3m` | `cdd_1m_3m_btcxdays` |
| `3m_6m` | `cdd_3m_6m_btcxdays` |
| `6m_1y` | `cdd_6m_1y_btcxdays` |
| `1y_2y` | `cdd_1y_2y_btcxdays` |
| `2y_3y` | `cdd_2y_3y_btcxdays` |
| `3y_5y` | `cdd_3y_5y_btcxdays` |
| `5y_7y` | `cdd_5y_7y_btcxdays` |
| `7y_10y` | `cdd_7y_10y_btcxdays` |
| `10y_plus` | `cdd_10y_plus_btcxdays` |

These labels must match the labels stored by `obm_spent_output_indexer.py` in the `daily_age_band_aggregates.age_band` field.

## Interpretation

`obm_cdd_age_band_btcxdays_daily` shows how daily Bitcoin Days Destroyed is distributed across output-age cohorts.

This metric is useful for:

- decomposing aggregate CDD by output age;
- distinguishing whether CDD spikes are driven by moderately old outputs or very old outputs;
- studying dormant-supply activation;
- comparing spent-value age composition with CDD age composition;
- validating aggregate `obm_cdd_btcxdays_daily`;
- constructing age-band shares of total daily CDD.

The metric should not be interpreted as a spent-value metric. It multiplies spent value by output age and is therefore measured in BTC-days. A small amount of very old spent value can contribute more CDD than a large amount of recently active spent value.

The metric is also not entity-adjusted. It does not identify users, entities, exchanges, custodians, change outputs, or self-transfers. As with other raw spent-output metrics, wallet consolidation, batching, custodial reorganization, and internal transfers may affect the observed CDD age distribution.

## Relationship with the spent-output indexer

This metric is exported from the table:

```text
daily_age_band_aggregates
```

in the SQLite database produced by:

```text
obm_spent_output_indexer.py
```

The relevant source fields are:

```text
date
age_band
cdd_sats_days
```

The indexer stores age-band CDD internally as satoshi-days:

```text
cdd_sats_days = sum(value_sats_i * age_days_i for outputs assigned to age band k)
```

for each date and age band.

The exporter converts satoshi-days to BTC-days:

```text
cdd_btcxdays = cdd_sats_days / 100000000
```

The exporter does not query Bitcoin Core. It only reads the already generated indexer database and writes a wide OBM CSV table.

## Reproducibility

The metric is generated by reading the persistent OBM spent-output indexer database.

For each date in the requested interval, the exporter:

1. opens the SQLite database generated by `obm_spent_output_indexer.py`;
2. verifies that the database metadata identify it as an OBM spent-output indexer database;
3. verifies that the requested ending date is not beyond the maximum processed date recorded by the indexer;
4. reads `date`, `age_band`, and `cdd_sats_days` from `daily_age_band_aggregates`;
5. initializes all age-band columns to zero for each requested date;
6. fills each available date-band pair using the corresponding `cdd_sats_days` value;
7. writes zero for missing date-band pairs;
8. converts satoshi-days to BTC-days by dividing by 100,000,000;
9. writes one wide row per UTC date;
10. optionally validates that the sum across age-band columns equals total CDD from `daily_aggregates.cdd_sats_days`;
11. optionally generates a stacked area plot.

The blockchain scan, previous-output resolution, output-age computation, CDD computation, and age-band assignment are performed by the shared spent-output indexer. This exporter is a deterministic transformation from the indexer database to a wide OBM CSV table.

## Typical exporter usage

Generate the CSV file:

```bash
python3 export_obm_cdd_age_band_btcxdays_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_cdd_age_band_btcxdays_daily.csv
```

Generate the CSV file with row-sum validation:

```bash
python3 export_obm_cdd_age_band_btcxdays_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_cdd_age_band_btcxdays_daily.csv \
  --validate_row_sums
```

Generate the CSV file and a stacked area plot:

```bash
python3 export_obm_cdd_age_band_btcxdays_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --state_db cache/obm_spent_output_indexer.sqlite \
  --output data/daily/obm_cdd_age_band_btcxdays_daily.csv \
  --validate_row_sums \
  --plot \
  --plot_output figures/obm_cdd_age_band_btcxdays_daily.png
```

If `--plot_output` is omitted while `--plot` is used, the plot is saved next to the CSV file with a `.png` extension.

## Standalone plotting utility

The standalone plot script reads an already generated CSV file and produces the same stacked area plot:

```bash
python3 plot_obm_cdd_age_band_btcxdays_daily.py \
  data/daily/obm_cdd_age_band_btcxdays_daily.csv \
  --output figures/obm_cdd_age_band_btcxdays_daily.png
```

The plotting utility does not compute the metric. It validates the expected wide CSV columns and then generates a stacked area chart where the filled areas represent the contribution of each age band to total daily Bitcoin Days Destroyed.

## Requirements

The exporter assumes:

- an existing SQLite database generated by `obm_spent_output_indexer.py`;
- Python 3;
- SQLite through Python's standard library;
- `matplotlib`, only if plot generation is requested.

The plot-only utility assumes:

- Python 3;
- an existing wide `obm_cdd_age_band_btcxdays_daily` CSV file;
- `matplotlib`.

Neither script requires:

- a running Bitcoin Core node;
- access to the Bitcoin Core JSON-RPC interface;
- direct block scanning;
- direct previous-output reconstruction at export time;
- address extraction;
- user clustering;
- entity identification;
- external price data;
- third-party APIs.

The heavy blockchain processing is performed by the spent-output indexer before this exporter is run.

## Indexer coverage assumption

The OBM spent-output indexer is designed to be built from the Bitcoin genesis block onward. Therefore, this exporter assumes that the indexer database contains a complete historical pass from block height 0 through the maximum processed height recorded in the metadata.

Under this invariant, a missing date-band pair in `daily_age_band_aggregates` for a requested UTC date does not indicate an unprocessed date. It indicates that no CDD contribution was assigned to that age band and date under the indexer's timestamp and age-band conventions. Such date-band pairs are therefore exported as zero.

Users should not use this exporter with a partially initialized or truncated indexer database unless they first verify that the requested date interval is fully covered.

## Missing-date and missing-band convention

For each requested date, the exporter creates one complete row with all age-band columns.

If a date-band pair is absent from `daily_age_band_aggregates`, the exporter writes:

```text
0.000000000000
```

for that age-band column.

This convention is appropriate because each age-band CDD value is a daily flow variable. If no CDD is assigned to an age band on a given UTC date, the value for that band is zero.

## Precision

The indexer stores age-band CDD internally as satoshi-days. The exporter converts each value to BTC-days and writes values with twelve decimal places:

```text
cdd_btcxdays = cdd_sats_days / 100000000
```

The additional decimal precision is useful because CDD can include fractional-day ages.

## Validation

Validation is divided into two groups: checks performed directly by the exporter or plot-only utility, and additional checks that are advisable for release preparation or independent auditing.

### Checks performed by the exporter

The exporter performs the following checks during execution:

- verifies that `--start_date` is not later than `--end_date`;
- verifies that the SQLite state database exists;
- opens the SQLite database and sets the connection to query-only mode;
- verifies that the database metadata contain the expected `indexer_id`;
- verifies that the database contains the required processing metadata, including `last_processed_height`, `last_processed_date`, and `max_processed_date`;
- verifies that the `daily_age_band_aggregates` table exists;
- verifies that `daily_age_band_aggregates` contains the required columns `date`, `age_band`, and `cdd_sats_days`;
- verifies that the requested `--end_date` is not later than the maximum date processed by the indexer;
- initializes every requested date with all expected age bands set to zero;
- rejects unexpected age-band labels found in the indexer database;
- rejects duplicate date-band aggregates;
- rejects negative `cdd_sats_days` values;
- converts satoshi-days to BTC-days by dividing by 100,000,000;
- writes one complete wide row per requested date;
- writes the output using the documented wide OBM schema;
- when `--validate_row_sums` is used, verifies that the sum across all age-band CDD columns equals `daily_aggregates.cdd_sats_days` for each date, within the configured tolerance;
- optionally generates a stacked area plot when `--plot` is used.

These checks ensure that the exporter is reading from the expected indexer database, that the requested interval is covered by the indexer, that all age-band labels are known, and that the generated CSV has one complete row per date.

### Checks performed by the plot-only utility

The standalone plotting utility performs the following checks:

- verifies that the input CSV file exists;
- verifies that the CSV file is non-empty;
- verifies that all expected wide-table columns are present;
- verifies that every row has `series_id = obm_cdd_age_band_btcxdays_daily`;
- verifies that every row has `unit = BTC-days`;
- verifies that every row has `frequency = daily`;
- verifies that all CDD age-band values are present and parseable as decimals;
- rejects negative CDD age-band values;
- rejects duplicate dates;
- sorts observations chronologically before plotting;
- generates a stacked area plot using all CDD age-band columns.

### Recommended additional checks

The following checks are not performed automatically in all workflows, but are recommended before publishing a release or using the table in empirical work:

- verify that every requested date appears exactly once in the output CSV;
- verify that all age-band CDD values are non-negative;
- run the exporter with `--validate_row_sums` whenever `daily_aggregates.cdd_sats_days` is available;
- verify that the sum across all CDD age-band columns equals `obm_cdd_btcxdays_daily` for every date when both are exported from the same indexer database and release version;
- verify that CDD contributions in young age bands are consistent with the maximum possible age in those bands;
- inspect unusually large spikes in old age bands and confirm that they correspond to large old-output movements;
- compare CDD age-band spikes with the spent-value age-band table to distinguish large value movements from old-age effects;
- check that the `release_version` field is consistent with the indexer metadata and with other OBM series generated from the same release;
- document any differences observed when comparing this table with external CDD age-distribution or coin-age analytics.

The main internal consistency relation is:

```text
sum of all CDD age-band columns = obm_cdd_btcxdays_daily
```

for every UTC date, provided that both datasets are generated from the same indexer database and release version.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, age-band boundaries, fractional-day treatment, entity adjustment, change-output treatment, transfer-value definition, and historical edge-case handling.

## Relationship with other OBM metrics

This table is closely related to:

```text
obm_cdd_btcxdays_daily
obm_spent_value_age_band_btc_daily
obm_spent_value_btc_daily
obm_dormancy_days_daily
```

The primary relationship is:

```text
obm_cdd_btcxdays_daily =
    cdd_0d_1d_btcxdays
  + cdd_1d_1w_btcxdays
  + cdd_1w_1m_btcxdays
  + cdd_1m_3m_btcxdays
  + cdd_3m_6m_btcxdays
  + cdd_6m_1y_btcxdays
  + cdd_1y_2y_btcxdays
  + cdd_2y_3y_btcxdays
  + cdd_3y_5y_btcxdays
  + cdd_5y_7y_btcxdays
  + cdd_7y_10y_btcxdays
  + cdd_10y_plus_btcxdays
```

for each date, subject to matching definitions and release versions.

This table complements `obm_spent_value_age_band_btc_daily`. The spent-value table shows how much BTC moved by age cohort, whereas the CDD age-band table shows how much coin age was destroyed by age cohort. Comparing the two helps distinguish value effects from age effects.

The table can also be used to build CDD age-band shares:

```text
cdd_age_band_btcxdays / obm_cdd_btcxdays_daily
```

for dates where total CDD is positive.

## Known limitations

Take into account that this metric:

- is exported from the OBM spent-output indexer database;
- depends on the correctness and completeness of the indexer run;
- inherits the UTC block-timestamp convention of the indexer;
- inherits the age computation and age-band assignment conventions used by the indexer;
- inherits the fractional-day age convention used for CDD;
- uses fixed age-band boundaries;
- is a raw spent-output coin-age table, not an entity-adjusted measure;
- includes self-transfers, change-related activity, batching, consolidation transactions, exchange operations, and custodial wallet management;
- does not identify users, entities, exchanges, custodians, or payment purpose;
- reports BTC-days, not BTC value or fiat-denominated value;
- is a wide vector-valued daily table rather than a scalar `value` series;
- may change if the underlying indexer definition, age-band convention, CDD convention, or release version changes.

Despite these limitations, `obm_cdd_age_band_btcxdays_daily` is a useful OBM coin-age distribution table. It provides a transparent decomposition of daily Bitcoin Days Destroyed by output age and complements scalar CDD, spent-value, dormancy, threshold-based CDD, and UTXO-flow metrics.
