# Open Bitcoin Metrics: Daily Block Weight in Weight Units

This repository provides the following time series of the **Open Bitcoin Metrics (OBM)** project:

```text
obm_block_weight_wu_daily
```

The series reports the total daily block weight, in Bitcoin weight units, of all blocks assigned to each UTC calendar day.

The computation script is:

```text
compute_obm_block_weight_wu_daily.py
```

## Metric summary

| Field | Value |
|---|---|
| Series identifier | `obm_block_weight_wu_daily` |
| Display name | Daily block weight in weight units |
| Unit | `WU` |
| Frequency | `daily` |
| Time convention | UTC calendar day |
| Source layer | Direct Bitcoin Core block scan |
| External data required | No |
| Main use | Block-space usage, fee-market analysis, normalization of transaction activity |

## Definition

`obm_block_weight_wu_daily` measures the total block weight of all Bitcoin blocks assigned to a given UTC calendar day.

Let `B_d` denote the set of blocks assigned to UTC date `d`. For each block `b`, let:

```text
Weight_b
```

denote its block weight in Bitcoin weight units, as returned by Bitcoin Core.

The metric is defined as:

```text
BlockWeightWU_d =
    sum over b in B_d Weight_b
```

A block is assigned to a UTC calendar date using its block timestamp as returned by Bitcoin Core:

```text
d(b) = UTCDate(block_time_b)
```

The unit is:

```text
WU
```

where `WU` denotes Bitcoin weight units.

## Interpretation

`obm_block_weight_wu_daily` measures the total amount of block weight included in the Bitcoin main chain on each UTC day. It is a block-space usage metric.

This metric is useful for:

- studying Bitcoin block-space utilization;
- complementing transaction count, fees, and block count;
- analyzing fee-market pressure;
- normalizing fees or transaction activity by block-space usage;
- distinguishing changes in transaction activity from changes in available block-space production;
- studying post-SegWit block-space dynamics, where weight is the relevant consensus-based capacity measure.

This metric is a total daily aggregate, not an average per block. If average daily block weight is needed, it can be derived as:

```text
average_block_weight_wu_daily =
    obm_block_weight_wu_daily / obm_block_count_daily
```

for dates where `obm_block_count_daily` is positive.

## Why block weight rather than block size?

Bitcoin block weight is the appropriate post-SegWit measure of block capacity and block-space usage. Traditional block size in bytes remains informative, but weight units better reflect the consensus constraint introduced by Segregated Witness.

Therefore, `obm_block_weight_wu_daily` is preferred as the primary OBM block-space metric. A separate block-size metric may still be useful for historical or comparative purposes, but it would not replace block weight as the main capacity-related variable.

## Data source and input requirements

The metric is computed directly from a running Bitcoin Core full node through the JSON-RPC interface.

For each block in the selected interval, the script retrieves the decoded block using:

```text
getblock <block_hash> 1
```

The script reads the block-level `weight` field returned by Bitcoin Core.

This metric requires:

- a synchronized Bitcoin Core full node;
- JSON-RPC access to the node;
- access to decoded block metadata.

This metric does not require:

- the OBM spent-output indexer database;
- `txindex=1`;
- previous-output reconstruction;
- transaction-level scanning;
- address extraction;
- user clustering;
- entity identification;
- external price data;
- third-party APIs.

Although `txindex=1` is useful for other OBM metrics, it is not required here because the metric uses only block-level metadata.

## Reproducibility

The metric is generated by scanning blocks in a date interval and summing their block weights.

For each selected date interval, the script:

1. connects to Bitcoin Core through JSON-RPC;
2. obtains the current chain tip using `getblockchaininfo`;
3. identifies an approximate block-height interval covering the requested UTC dates;
4. expands the interval using `--height_margin`;
5. scans every block in the expanded interval;
6. assigns each block to a UTC calendar date using the block timestamp;
7. skips blocks outside the requested date interval;
8. reads each counted block's `weight` field;
9. sums block weights by UTC date;
10. initializes all requested calendar dates to zero;
11. writes one row per UTC date using the standard OBM schema;
12. optionally generates a plot.

The height-margin expansion is used because Bitcoin block timestamps are not strictly monotonic with respect to block height. The expanded scan interval reduces the risk of missing boundary blocks whose timestamps fall inside the selected UTC dates.

## Typical script usage

Generate the CSV file using Bitcoin Core cookie authentication:

```bash
python3 compute_obm_block_weight_wu_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --use_default_cookie \
  --output data/daily/obm_block_weight_wu_daily.csv
```

Generate the CSV file and a plot:

```bash
python3 compute_obm_block_weight_wu_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --use_default_cookie \
  --output data/daily/obm_block_weight_wu_daily.csv \
  --plot \
  --plot_output figures/obm_block_weight_wu_daily.png
```

Generate the CSV file using explicit RPC credentials:

```bash
python3 compute_obm_block_weight_wu_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --rpc_url http://127.0.0.1:8332 \
  --rpc_user my_rpc_user \
  --rpc_password my_rpc_password \
  --output data/daily/obm_block_weight_wu_daily.csv
```

RPC credentials can also be supplied through environment variables:

```bash
export BITCOIN_RPC_URL="http://127.0.0.1:8332"
export BITCOIN_RPC_USER="my_rpc_user"
export BITCOIN_RPC_PASSWORD="my_rpc_password"
```

Then run:

```bash
python3 compute_obm_block_weight_wu_daily.py \
  --start_date 2009-01-01 \
  --end_date 2024-01-31 \
  --output data/daily/obm_block_weight_wu_daily.csv
```

## Command-line arguments

| Argument | Description |
|---|---|
| `--start_date` | Starting UTC date, inclusive, in `YYYY-MM-DD` format |
| `--end_date` | Ending UTC date, inclusive, in `YYYY-MM-DD` format |
| `--rpc_url` | Bitcoin Core RPC URL |
| `--rpc_user` | Bitcoin Core RPC username |
| `--rpc_password` | Bitcoin Core RPC password |
| `--cookie_path` | Path to Bitcoin Core RPC cookie file |
| `--use_default_cookie` | Use the default cookie path `~/.bitcoin/.cookie` |
| `--rpc_timeout` | RPC timeout in seconds |
| `--height_margin` | Extra blocks scanned before and after the approximate height interval |
| `--output` | Output CSV file path |
| `--release_version` | Dataset release version written to the output |
| `--plot` | Generate a plot of the resulting series |
| `--plot_output` | Output path for the plot |
| `--quiet` | Suppress diagnostic messages printed to standard error |

The default output file is:

```text
obm_block_weight_wu_daily.csv
```

The default release version is:

```text
OBM v0.1.0
```

The default height margin is:

```text
288 blocks
```

This corresponds to approximately two days of expected Bitcoin block production.

## Data format

The output CSV file follows the standard OBM scalar schema:

```text
date,series_id,value,unit,frequency,release_version
```

Example:

```csv
date,series_id,value,unit,frequency,release_version
2024-01-01,obm_block_weight_wu_daily,568923456,WU,daily,OBM v0.1.0
2024-01-02,obm_block_weight_wu_daily,541234987,WU,daily,OBM v0.1.0
```

### Columns

| Column | Description |
|---|---|
| `date` | UTC calendar date in `YYYY-MM-DD` format |
| `series_id` | Stable OBM identifier: `obm_block_weight_wu_daily` |
| `value` | Total block weight of all blocks assigned to the UTC date |
| `unit` | Measurement unit: `WU` |
| `frequency` | Observation frequency: `daily` |
| `release_version` | OBM dataset release version |

## Missing-date convention

The script initializes every requested UTC date to zero before scanning blocks.

If no block is assigned to a selected UTC date, the script writes:

```text
0
```

This convention is appropriate because the metric is a daily block-level aggregate.

## Precision

Block weight is an integer quantity measured in weight units. The script accumulates daily block weight as integers and writes integer values to the output CSV.

No floating-point arithmetic is required for the metric itself.

## Validation

Validation is divided into two groups: checks performed directly by the script, and additional checks that are advisable for release preparation or independent auditing.

### Checks performed by the script

The script performs the following checks during execution:

- verifies that `--start_date` is not later than `--end_date`;
- verifies that `--height_margin` is non-negative;
- verifies that the RPC authentication configuration is valid;
- verifies that the RPC cookie file exists and has valid format when cookie authentication is used;
- connects to Bitcoin Core through JSON-RPC;
- obtains the current chain tip using `getblockchaininfo`;
- locates an approximate block-height interval for the requested timestamp range;
- expands the scan interval using `--height_margin`;
- scans all blocks in the expanded interval;
- assigns each scanned block to a UTC date using the block timestamp;
- counts only blocks whose UTC date lies inside the requested interval;
- verifies that each counted block contains a `weight` field;
- rejects negative block-weight values;
- initializes all selected UTC dates with zero;
- writes one output row per selected UTC date;
- writes the output using the standard OBM schema;
- optionally generates a plot when `--plot` is used;
- prints diagnostics including counted blocks and scanned blocks, unless `--quiet` is used.

These checks ensure that the script scans a sufficiently broad block interval, uses the block-level weight field, preserves one row per selected date, and writes integer weight-unit values.

### Recommended additional checks

The following checks are not performed automatically by the script, but are recommended before publishing a release or using the series in empirical work:

- verify that every requested date appears exactly once in the output CSV;
- verify that all exported values are non-negative integers;
- verify that early dates with no blocks have zero block weight;
- compare the number of counted blocks with `obm_block_count_daily`;
- compute an average block weight diagnostic:
  ```text
  obm_block_weight_wu_daily / obm_block_count_daily
  ```
  for dates where block count is positive;
- verify that average block weight does not exceed the consensus block weight limit for ordinary post-SegWit blocks;
- inspect unusually large or unusually small daily values and compare them with daily block count;
- compare selected periods with independent blockchain explorers or data providers as diagnostics;
- document any differences observed when comparing this series with external block-size or block-weight metrics.

External comparisons should be interpreted cautiously because providers may differ in timestamp convention, treatment of reorganizations, smoothing, or whether they report total daily weight, average weight, size in bytes, or percentage of block capacity used.

## Relationship with other OBM metrics

This metric is closely related to:

```text
obm_block_count_daily
obm_tx_count_daily
obm_fees_btc_daily
obm_raw_output_value_btc_daily
```

The relationship with block count is especially important. The total daily block weight depends partly on how many blocks are assigned to the day. A useful derived diagnostic is:

```text
average_block_weight_wu_daily =
    obm_block_weight_wu_daily / obm_block_count_daily
```

for dates where block count is positive.

This derived average can help separate block-space usage per block from daily variation caused by a larger or smaller number of blocks.

The metric is also useful in fee-market analysis. When combined with total daily fees, it can support a fee-per-weight-unit measure:

```text
fees_per_wu_daily =
    obm_fees_btc_daily / obm_block_weight_wu_daily
```

for dates where block weight is positive.

## Known limitations

Take into account that this metric:

- measures total daily block weight, not average block weight;
- depends partly on the number of blocks assigned to each UTC date;
- depends on the block timestamp convention used to assign blocks to UTC dates;
- does not directly measure transaction demand, economic value, user activity, or fee pressure;
- does not distinguish witness and non-witness data beyond the consensus weight formula already embedded in the block weight field;
- may differ from metrics reported as block size in bytes or capacity-utilization percentage;
- is directly computed from decoded block metadata and does not require the spent-output indexer;
- may differ from provider series that smooth the data or use different daily boundaries.

Despite these limitations, `obm_block_weight_wu_daily` is a useful OBM block-space series. It provides a transparent, full-node-derived measure of total daily block-space usage and complements block count, transaction count, fees, and raw output value.
